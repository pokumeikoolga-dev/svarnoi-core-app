# ADR-0004: автоматическая отправка после проверки и временное замещение

- Статус: принято для проектирования
- Дата: 2026-07-28

## Контекст

Цель продукта — убрать ручной поиск чата и пересылку материалов, не убрав обязательный контроль. Для разных исходящих материалов требуются разные проверяющие и разные юридические последствия.

Дополнительно мастер-приемщик иногда отсутствует, а технический процесс не должен останавливаться или получать постоянные избыточные права у всех мастеров.

## Решение

### Проверка клиентского фотоотчета

Для обычного клиентского фотоотчета создается `PublicationReview` типа `CLIENT_PROGRESS_REPORT`.

- мастер формирует версию отчета;
- офис-менеджер принимает или возвращает ее;
- возврат требует причины;
- после `approved` система автоматически отправляет клиенту именно принятую версию;
- повторное событие не создает повторную отправку.

Техническая проверка и проверка публикации не объединяются: они отвечают на разные вопросы.

### Дополнительные работы

Цепочка хранится явными состояниями:

`draft → submitted → technically_approved → price_ready → sent_to_client → client_approved/client_rejected → merged_into_scope`

Автоматическая отправка разрешена только при одновременном выполнении условий:

- мастер-приемщик принял точную техническую версию;
- цена получена из утвержденного источника и готова к отправке;
- сообщение связано с текущей версией заказа и владельцем автомобиля.

Согласованный объем, итоговая сумма и часы исполнителя меняются только после `client_approved`. Backend выполняет перерасчет; AI может только объяснить результат.

### Уведомление о готовности

Принятый `FINAL_CHECKLIST_REVIEW` создает одно автоматическое уведомление владельцу автомобиля о готовности к выдаче.

Если подтвержденный ответ клиента не получен за настраиваемый интервал, система создает офис-менеджеру задачу на звонок. Интервал задается конфигурацией после решения собственника.

### Временное замещение

Замещение мастер-приемщика моделируется сущностью `RoleDelegation`, а не постоянной второй ролью у мастера:

- кто делегировал полномочие;
- кто замещает;
- набор разрешенных действий;
- дата и время начала;
- дата и время окончания;
- причина;
- журнал действий от имени замещающего.

Самоназначение замещающим запрещено. Истекшее делегирование автоматически прекращает действовать.

### Доступ владельца автомобиля

Доступ клиента моделируется `ClientAccessGrant`, связанным с конкретным владельцем автомобиля и заказом. Номер телефона или договора сам по себе не является достаточной авторизацией.

Точная политика доступа после завершения ремонта остается открытым решением.

## Надежность и аудит

Каждая автоматическая отправка:

- имеет idempotency key;
- хранит тип сообщения, заказ, получателя, версию материала и событие-основание;
- записывает время попытки, доставки и ошибку;
- повторяется безопасно без дублей;
- не меняет бизнес-статус при ошибке генеративного AI.

## Последствия

- сотрудник проверяет материал, но не ищет клиентский чат;
- автоматизация не обходит человека в контрольной точке;
- согласие клиента нельзя спутать с внутренним `accept`;
- замещение не размывает постоянную матрицу прав;
- можно тестировать каждый автоматический переход отдельно.

## Не решено этим ADR

- срок ожидания ответа на приглашение к выдаче;
- срок клиентского доступа после закрытия заказа;
- официальный назначающий временного заместителя;
- юридический канал подписания документов.

# Архитектурные правила

## Базовый подход

- Начальная архитектура — модульный монолит, не микросервисы.
- Главная бизнес-сущность — заказ-наряд конкретного визита автомобиля.
- Внешним идентификатором служит номер договора; внутренний ID создает система.
- Один автомобиль может иметь много исторических заказов.
- По умолчанию у автомобиля один активный заказ. Исключение добавляется только после подтверждения потребности.

## Границы модулей

- identity and access;
- customers and vehicles;
- service orders;
- diagnostics and estimates;
- media;
- additional-work approvals;
- timeline and notifications;
- audit;
- AI Core adapter.

Логические границы не означают отдельные сервисы или базы на первом этапе.

## Согласования

- Первоначальный и дополнительный перечни работ хранятся версиями.
- Предложение нельзя изменять после отправки клиенту.
- Решение клиента относится к точной версии предложения.
- Текст «согласовано» может определить намерение, но не заменяет подтверждение точного списка и стоимости.
- Итоговый перечень рассчитывает backend; AI формирует только понятное представление.

## Интеграции

- Существующий Telegram-бот цен подключается через адаптер.
- Его формулировки, порядок и цены не переписываются незаметно.
- Viber остается резервным процессом; интеграция с Viber в ранний scope не входит.
- Google Sheets сначала изучаются и экспортируются. Двусторонняя синхронизация требует отдельного решения.

## Нефункциональные требования

- Любое клиентское действие связано с заказом.
- Загрузка фото не требует поиска клиентского диалога.
- Ошибка AI не блокирует основной процесс.
- Критические операции идемпотентны и журналируются.
- Доступ строится по принципу минимально необходимых прав.

## Рабочие интерфейсы по ролям

- Единая система не означает одинаковый интерфейс для всех ролей.
- Все рабочие действия привязаны к `ServiceOrder`, но домашний экран и видимость данных определяются ролью и назначением на заказ.
- Мастер по умолчанию видит одну назначенную машину, текущий этап, согласованный список и только короткие производственные действия.
- Мастер не ищет клиента, договор или чат перед загрузкой фото.
- Основные действия мастера: фото этапа, найденная дополнительная работа/проблема и завершение этапа.
- Менеджер работает из очереди действий, требующих решения, и из полной операционной карточки заказа.
- Клиент видит только опубликованные клиентские данные собственных заказов.
- Подрядчик получает доступ только к назначенной операции, а не ко всей карточке клиента.
- Клиентская цена, внутреннее вознаграждение, внутренние заметки и клиентские материалы имеют отдельные уровни видимости.
- Цвет не является единственным способом показать статус; критические статусы всегда имеют текст.

## Производственный процесс

- Жизненный цикл заказа и производственная контрольная точка хранятся отдельно.
- Ожидание решения клиента не стирает фактический этап производства.
- Контрольные точки фотоотчета настраиваются под конкретный заказ; неприменимые этапы не показываются мастеру.
- Каждое фото имеет заказ, этап, автора, время и тип видимости.
- Обычный фотоотчет и материал для дополнительного согласования — разные типы событий.
- Дополнительная запись явно классифицируется как работа, запчасть или рекомендация.
- Перед отправкой фото интерфейс повторно показывает автомобиль и этап.
- При слабой связи загрузка имеет безопасную очередь и видимый статус синхронизации.

## Telegram и файлы

- Telegram `initData` всегда проверяется на backend; frontend не считается доверенной стороной.
- Telegram ID связывается с учетной записью и ролью сотрудника.
- Номер телефона или номер договора сами по себе не дают доступ к заказу.
- Фото и документы хранятся в приватном объектном хранилище, а не в GitHub и не по постоянным публичным ссылкам.
- Для просмотра файлов используются ограниченные по времени ссылки.
